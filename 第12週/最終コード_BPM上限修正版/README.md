# 最終コード（BPM上限修正版）

`第12週/最終コード/` をベースに，計画書との差異チェックで見つかった
**BPM上限の不整合（実装240 vs 計画書の想定200）を修正**したもの。
それ以外の内容・構成は`最終コード/`と同一。

## このバージョンでの変更点

計画書の変更履歴（v5.0, 2026年6月19日）では，BPM通信遅延の判定基準を300ms以内とした根拠として
「設定しているBPMの上限200BPMに基づき，次の拍までに反映されれば良い」としていた
（BPM200 → 1拍=300ms）。しかし実装コードは`BPM_MAX = 240.0`となっており，
BPM240では1拍=250msとなるため，300ms遅延だと次拍に間に合わない場合がある，という
理論的な不整合があった。今回，計画書側の想定に実装を合わせる形で以下を修正した。

| ファイル | 修正内容 |
|---|---|
| `指揮者/Arduino/conductor/conductor.ino` | `BPM_MAX = 240.0` → `200.0` |
| `バイオリン/Arduino/violin/violin.ino` | 受信BPMの上限チェック `<= 240` → `<= 200` |
| `フルート/Arduino/flute/flute.ino` | 受信BPMの上限チェック `<= 240` → `<= 200` |
| `チェロ/Arduino/cello/cello.ino` | 受信BPMの上限チェック `<= 240` → `<= 200` |
| `コントラバス/Arduino/contrabass/contrabass.ino` | 受信BPMの上限チェック `<= 240` → `<= 200` |

※バイオリン／チェロ／フルートは元々共通コードのため（下記参照），この4ファイルで
BPM上限は完全に統一されている。

※この修正はまだ実機・システムテストでの動作確認を行っていない。評価会前に
BPM上限付近（190〜200）での再生・停止・テンポ変更が正常に動作するか，
一度は通しで確認することを推奨する。

## 重要：バイオリン／チェロ／フルートのArduinoは共通コード

輪唱（カノン）であるため，バイオリン・チェロ・フルートは同じメロディーを時間差で演奏するだけで，
Arduino側のロジック（レーザ受信・拍カウント・メロディ配列）は3楽器とも同一。
`Ketugou_instrument_var11.ino`を3楽器共通のArduinoコードとして採用した
（チェロの「Arduino未発見」問題もこれで解消）。コントラバスのみメロディを8音ベースパターンに
差し替えた独自コード。Processing側（音色）は当然ながら4楽器ともそれぞれ別。

## 未解決の問題

- **var11採用は実機での動作未確認。** 旧候補`第11週/Ketugou_var6-1782884271057/`は
  アーキテクチャ自体が古い（ブロッキング方式）ため不採用としたが，本番前に一度は
  3楽器同時での通し動作を確認すること。
- **共通コードのANGLE_REST/PLAYとブロック周期は，コントラバス側コードのコメントが
  想定する値（8小節毎）と異なる（4小節毎になっている）。** コントラバス側との整合性は未検証。
- 元の計画書に記載のファイル名（`vi.ino`/`vi_pro.pde`等）とは命名が一致していない。
  実際の作業ファイル名をそのまま踏襲し，フォルダ名で役割を明示する方針とした。

## テスト専用コードとの違い

テスト専用実装（楽器を「楽器A/B/C/D」等の匿名ラベルで扱う）であり，ここには含めていない。
